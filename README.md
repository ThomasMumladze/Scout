# Scout

LLM-ზე დაფუძნებული დეველოპერ-ასისტენტი, რომელიც ლოკალური პროექტის ფაილებზე, git ისტორიასა და ამოცანების სიაზე პასუხობს კითხვებს.
აგენტი C#-ზეა დაწერილი, მოდელი (Qwen2.5-3B-Instruct, GGUF ფორმატი) კი **სრულად ლოკალურად** გადის LLamaSharp-ით. ინტერნეტი და API გასაღები საჭირო არ არის.

## რა პრობლემას ჭრის და ვისთვის

დეველოპერი, რომელიც რამდენიმე პროექტზე მუშაობს, დროს კარგავს იმის ძიებაში, თუ სად არის რაღაც განსაზღვრული, რა შეიცვალა ბოლო დროს და რა ამოცანები აქვს გასაკეთებელი.
Scout ბუნებრივ ენაზე დასმულ კითხვას იღებს, **თვითონ წყვეტს**, რომელი ხელსაწყო გამოიყენოს, და პასუხს რეალურ ფაილებსა და git ისტორიაზე დაყრდნობით აბრუნებს.
მომხმარებელი: დეველოპერი, რომელიც ლოკალურ პროექტებთან მუშაობს.

## PEAS

- **შესრულების საზომი:** პასუხის სისწორე კოდის ბაზის შესახებ, ხელსაწყოს სწორი არჩევა, ნაბიჯების მცირე რაოდენობა და ის რომ აგენტი არ ამბობს "გავაკეთე", როცა მოქმედება რეალურად არ შეუსრულებია.
- **გარემო:** ლოკალური პროექტის საქაღალდე (წყარო ფაილები და git რეპოზიტორი), ამოცანების JSON ფაილი და მომხმარებლის კითხვები.
- **აქტუატორები:** ტექსტური პასუხი კონსოლში და ხელსაწყოების გამოძახება (ფაილების ძებნა, git ბრძანება, ამოცანების ფაილში ჩაწერა).
- **სენსორები:** მომხმარებლის ტექსტური შეყვანა და ხელსაწყოების მიერ დაბრუნებული შედეგები.

## გარემოს თვისებები

1. **ნაწილობრივ დაკვირვებადი:** აგენტი პროექტს მთლიანად ვერ ხედავს, მხოლოდ ხელსაწყოების შედეგებს იღებს.
2. ერთსა და იმავე ფაილებზე ერთი და იგივე ძებნა ყოველთვის ერთსა და იმავე შედეგს აბრუნებს.
3. **თანმიმდევრული:** ერთი ხელსაწყოს შედეგი განსაზღვრავს შემდეგ ნაბიჯს, ამიტომ პასუხისთვის რამდენიმე ნაბიჯი შეიძლება დასჭირდეს.
4. **სტატიკური:** აგენტის მსჯელობისას ფაილები არ იცვლება, რადგან პროექტს ამ დროს მხოლოდ მომხმარებელი ეხება და ის პასუხს ელოდება.
5. **ერთი აგენტი:** მოქმედებს მხოლოდ ერთი აგენტი, მომხმარებელი მხოლოდ კითხვებს სვამს და მასთან კონკურენცია არ არსებობს.
6. **აგენტისთვის ცნობილია:** ფაილური სისტემის, git-ისა და ხელსაწყოების ქცევის წესები წინასწარ.

## აგენტის ტიპი

**Goal-based აგენტი.** მიზანია მომხმარებლის კითხვაზე პასუხის გაცემა, ენის მოდელი კი ხელსაწყოების იმ თანმიმდევრობას ირჩევს, რომელიც ამ მიზანს მიაღწევს.
Simple reflex აგენტი არ გამოდგებოდა, რადგან გარემო ნაწილობრივ დაკვირვებადი და თანმიმდევრულია: მოქმედების არჩევა წინა ნაბიჯების შედეგებზეა დამოკიდებული.
Utility-based აგენტი კი ზედმეტია, რადგან არ გვაქვს კონკურენტი შედეგების შედარება.

## როგორ მუშაობს

1. მომხმარებელი სვავს კითხვას.
2. აგენტი მოდელს უგზავნის სისტემურ პრომპტს (წესები და ხელსაწყოების სია მაგალითებით) და კითხვას.
3. მოდელი პასუხობს JSON-ის ერთ-ერთი ფორმით:
    - `{"tool": "სახელი", "args": {...}}` — ხელსაწყოს გამოძახება;
    - `{"final_answer": "ტექსტი"}` — საბოლოო პასუხი.
4. აგენტი უშვებს არჩეულ ხელსაწყოს და შედეგს მოდელს უბრუნებს.
5. ციკლი მეორდება, სანამ მოდელი საბოლოო პასუხს არ დაწერს (მაქსიმუმ 5 ნაბიჯი).

გადაწყვეტილებას იღებს მოდელი, კოდში არ არის წინასწარ ჩაწერილი `if`-ები კითხვის ტიპის მიხედვით.

## ხელსაწყოები

ყველა ხელსაწყოს აქვს სახელი, აღწერა, პარამეტრები და დაბრუნებული მნიშვნელობა (კოდში XML კომენტარებად).

| ხელსაწყო       | რას აკეთებს                                               | პარამეტრები                                                                   | აბრუნებს                                             |
| -------------- | --------------------------------------------------------- | ----------------------------------------------------------------------------- | ---------------------------------------------------- |
| `search_files` | ეძებს ტექსტს ფაილების **შიგნით** (კლასი, მეთოდი და ა.შ.)  | `query` — მოსაძებნი იდენტიფიკატორი                                            | მაქსიმუმ 10 დამთხვევას ფორმატით `ფაილი:ხაზი: ტექსტი` |
| `find_files`   | პოულობს ფაილს **სახელით** მთელ პროექტში, ნებისმიერი ტიპის | `query` — ფაილის სახელი ან მისი ნაწილი                                        | მაქსიმუმ 20 გზას პროექტის საქაღალდის მიმართ          |
| `git_log`      | აჩვენებს ბოლო git კომიტებს                                | `count` — რამდენი კომიტი (1-20, ნაგულისხმევი 5)                               | ხაზებს ფორმატით `ჰეში თარიღი შეტყობინება`            |
| `todo`         | პირადი ამოცანების სია JSON ფაილში                         | `action` (`add`, `list` ან `done`), `text` (დამატებისას), `id` (დასრულებისას) | დადასტურებას ან ამოცანების სიას                      |

ხელსაწყოები ერთმანეთისგან განსხვავებულია: ტექსტის ძებნა ფაილებში, ფაილის პოვნა სახელით, git ისტორია და მონაცემების შენახვა.

## მაგალითები: რა შეგიძლია ჰკითხო

**კოდში ძებნა (`search_files`):**

- `Where is ToolCallParser defined?`
- `Where is AgentService used?`
- `Which file configures MaxSteps?`

**ფაილის პოვნა სახელით (`find_files`):**

- `Where is AgentServiceTests.cs located?`
- `Does README.md exist?`
- `Find the file ITool.cs`

**git ისტორია (`git_log`):**

- `What did I commit recently?`
- `Show the last 10 commits`

**ამოცანები (`todo`):**

- `Add a task: write README`
- `Show my tasks`
- `Mark task 1 as done`

**კითხვები, რომლებზეც აგენტმა უნდა თქვას რომ ვერ უპსუხებს:**

- `What is the weather in Tbilisi?` (შესაბამისი ხელსაწყო არ არსებობს)
- `Delete all .bak files` (ყველა ხელსაწყო მხოლოდ კითხულობს ან უსაფრთხოდ წერს თავის სიაში)

კონსოლში `[model]` და `[tool]` ხაზები აჩვენებს, რა გადაწყვიტა მოდელმა და რა დააბრუნა ხელსაწყომ. ეს დებაგისთვის სასარგებლოა.

## როგორ გაეშვება

### საჭირო პროგრამები

- [.NET 10 SDK](https://dotnet.microsoft.com/download)
- Visual Studio (არჩევითი, `dotnet` ბრძანებებითაც გაეშვება ან უბრალოდ debug ღილაკზე ხელის დაჭერით)
- Git (საჭიროა `git_log` ხელსაწყოსთვის, უნდა იყოს PATH-ში)
- დაახლოებით 4 GB თავისუფალი RAM

### ნაბიჯები

1. დააკლონე repo და გადადი მის საქაღალდეში.
2. ჩამოტვირთე მოდელი Hugging Face-იდან: რეპო `Qwen/Qwen2.5-3B-Instruct-GGUF`, ფაილი `qwen2.5-3b-instruct-q4_k_m.gguf` (დაახლოებით 2 GB). token არ არის საჭირო. ფაილი ჩადე `Scout/models/` საქაღალდეში (შექმენი, თუ არ არსებობს). საქაღალდე git-ში არ ატვირთება.
3. გახსენი `Scout/Program.cs` და შეცვალე სამი path შენს კომპიუტერზე:
    ```csharp
    const string ModelPath = @"C:\...\models\qwen2.5-3b-instruct-q4_k_m.gguf";
    const string ProjectRoot = @"C:\...\პროექტი-რომელშიც-ეძებ";
    const string TodoFile = @"C:\...\data\todos.json";
    ```
4. გაუშვი:
    ```
    dotnet run --project Scout
    ```
5. პირველი ჩატვირთვა რამდენიმე წამს გრძელდება ("Loading model..."). როცა გამოჩნდება `Scout is ready`, დასვი კითხვა. გასასვლელად ჩაწერე `exit`.

### ტესტები

```
dotnet test
```

ტესტები მოდელის გარეშე გადის: აგენტის ციკლი მოწმდება ყალბი მოდელით (`FakeLlmClient`).

### GPU (არჩევითი)

ნაგულისხმევად მოდელი CPU-ზე გადის. NVIDIA GPU-ს შემთხვევაში `LLamaSharp.Backend.Cpu` პაკეტი ჩაანაცვლე `LLamaSharp.Backend.Cuda12`-ით და `LlmOptions`-ში გაზარდე `GpuLayerCount`.

## არქიტექტურა

Clean Architecture, დამოკიდებულება მხოლოდ შიგნისკენ მიდის:

| პროექტი              | შიგთავსი                                                                                           |
| -------------------- | -------------------------------------------------------------------------------------------------- |
| `Dex.Domain`         | ენტიტები: `ChatMessage`, `Role`, `ToolCall`, `TodoItem`                                            |
| `Dex.Application`    | აგენტის ციკლი (`AgentService`), JSON პარსერი, პრომპტის აგება, ინტერფეისები (`ILlmClient`, `ITool`) |
| `Dex.Infrastructure` | LLamaSharp კლიენტი და ხელსაწყოები                                                                  |
| `Scout`              | კონსოლის ინტერფეისი და ყველაფრის მიერთება                                                          |
| `Dex.Tests`          | xUnit ტესტები                                                                                      |

აგენტის ლოგიკა LLamaSharp-ს არ იცნობს, მხოლოდ `ILlmClient` ინტერფეისს. ამიტომ მოდელის შეცვლა (მაგალითად, სხვა ბიბლიოთეკაზე ან API-ზე) ერთი ახალი კლასია, აგენტი არ იცვლება, ტესტებში კი მოდელის ადგილას ყალბი კლიენტი დგას.

## როგორ მუშაობს აგენტი

აგენტის ციკლი ამუშავებს ოთხ შემთხვევას: მოდელმა არასწორი JSON დააბრუნა (ორჯერ ვთხოვთ გასწორებას, მერე ვნებდებით), არარსებული ხელსაწყო აირჩია (ვუბრუნებთ არსებული ხელსაწყოების სიას), ხელსაწყომ შეცდომა დააბრუნა (არასწორი პარამეტრი, git-ის ჩავარდნა ან დაზიანებული ფაილი გადადის მოდელთან ტექსტად და არ ანგრევს აგენტს) ან მოდელი ვერ მივიდა პასუხამდე (მაქსიმუმ 5 ნაბიჯი).
ყველაზე სუსტი ადგილი თვითონ პატარა მოდელია: ხანდახან არასწორ query-ს წერს (მაგ. `def ToolCallParser`), ერთი წარუმატებელი ძებნის შემდეგ ნებდება, ამბობს რომ ხელსაწყო არ არსებობს, მაშინაც კი, როცა არსებობს, JSON-ში ბექსლეშებს არასწორად წერს, ან ერთ პასუხში `tool` და `final_answer` ერთად წერს და ისე ამტკიცებს, რომ მოქმედება შესრულდა, რომ ხელსაწყო არც გაშვებულა.
კონტექსტის ფანჯარა 4096 ტოკენია, ამიტომ ძალიან გრძელი ხელსაწყოს შედეგი პასუხს დააზიანებდა (ამიტომ ვზღუდავთ ძებნას 10, ფაილების პოვნას კი 20 შედეგით).

## შეზღუდვები
